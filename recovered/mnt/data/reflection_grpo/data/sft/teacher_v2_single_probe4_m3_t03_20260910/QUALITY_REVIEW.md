# M3 单次调用反思 + 续推：v2 小样本审核

结论：单次调用的字段组织可行。这次三个错误样本均生成正确续推终值，三个反思都没有直接给出所求最终答案；相比上一轮有明显的输出分工改善。但严格按当前 prompt 审核，只有系数和题可作为直接使用的示例；糖果题、固定点题仍混入 teacher 新推导的状态，不能仅凭数值正确把三条全部放行。

## 实际执行

- 使用与上一轮完全相同的 4 条学生回答，samples.json 逐字节一致。
- model=MiniMax-M3，temperature=0.3，top_p=0.95，max_completion_tokens=16384，thinking.type=adaptive，reasoning_split=true。
- 地址为 https://api.minimaxi.com/v1/chat/completions。
- 每条恰好调用 1 次，合计 4 次，无重试、无二阶段 API 调用。4/4 HTTP 200，4/4 响应模型为 M3，4/4 finish_reason=stop，4/4 返回非空独立 thinking 字段，无截断。
- 3 条原始 content 是直接 JSON；1 条外包 JSON 代码围栏，程序按预先声明的规则去围栏并记录，但未修改原始响应。
- usage 合计：prompt_tokens=7,747，completion_tokens=4,667，total_tokens=12,414。上一轮同组题的两次调用设计实际共 5 次请求、24,212 tokens；这只是两次小样本运行的消耗，不能推断全量平均成本或准确率。
- 3 条错误对象通过结构校验；1 条 incomplete 对象因 verified_states 未按要求置空，被严格 schema 拒收。它的数学筛除判断仍然合理。
- Perfect API 请求 0。未导出 SFT 训练记录，未启动全量标注，没有修改 prompt 快照、学生回答或原始标签。
- 21 项离线解析、schema、空字段、重复键、异常 JSON、标签与答案渲染检查通过。冻结输入、样本哈希和请求留档齐全。

## 逐条复核

### 0.6B k1：合并数字与糖果

反思正确指出：学生假定每次都是 1×1，但合并会产生更大的数字。new_direction 建议研究平方和变化，没有给出 325。

续推使用每次平方和增加 2ab 的关系，计算 (26²−26)/2=325。程序追加 boxed 后，本地答案提取为 325，compute_math_score=1.0；人工也确认主要计算正确。

保留问题：

- verified_states 把“总和始终为 26”作为已有状态，但学生在错误前没有建立这个结论。它是正确的新推论，应在续推中说明，而不是冒充学生既有进展。
- new_direction 已写出平方和变化公式和最后剩下 26，超过了本版“先给操作、续推才执行修复”的严格边界，尽管没有直接给最终答案。
- 续推末尾额外提到“总选最大的两个数”并使用 Huffman-style 的命名。该具体顺序确实也能得到 325，但这里无需引入贪心策略或算法名称；证明应明确完整合并的总量与顺序无关。

因此这条不是原样可用的严格合格示例，不能只看答案分数。

### 0.6B k2：对数固定点

续推正确推出 A=(-2,-8/9)、b=-1，最后 f(log_3 2)=1。本地答案提取为 1，compute_math_score=1.0，人工确认计算正确。

反思没有直接写出所求终值 1，也没有引用错误原句。但存在：

- verified_states 提前加入“对数项必须为 0”这个 teacher 新推导的结论，学生错误前没有得到它。
- error_reason 与 new_direction 已计算 A 的坐标，不完全符合本版反思先只给操作方向的要求。
- 错因聚焦于后面的“随意设 x=1”，漏掉较早丢失 −8/9 平移项的问题。虽然路线能修复答案，但不满足当前 prompt 的首个实质错误要求。

严格人工验收暂不放行，不能为得到好看的通过率放宽规则。

### 4B k2：以 x+2 为基底的系数和

这条可以作为新版格式的合格示例：

- verified_states 只保留多项式恒等式与展开基底等题目条件。
- error_reason 指出错误地把基底 x+2 当成 x。
- new_direction 只要求在 x=-1 处代入，没有提前计算最终答案。
- reasoning 明确定义 y=x+2，再解释 y=1 对应 x=-1，并算出 −2。
- final_answer 为 −2，与续推一致；程序追加 boxed 后本地判分为 1.0。

修正规则 x=-1 出现在错因解释中是必要的基底辨析，不等于泄露题目所求的最终系数和。

### 4B k3：等价分式未化简完成

M3 返回 verdict=incomplete，正确指出学生的等价变形成立，只是没有使用 ab=1 完成最后约分；没有制造虚假错误。

它同时返回了一段非空 verified_states，违反本版本要求非 incorrect 记录清空全部训练字段的 schema，因此程序报告 ValidationError。这个失败属于审核记录格式问题，不是数学诊断错误，也不应产生反思训练对。

原始响应外的一个 JSON 代码围栏被程序正常去除并记录；没有人工清空状态字段后把该对象伪装成原始合规输出。

## 长度与训练映射

按各学生本地 tokenizer、enable_thinking=false、现有两阶段训练模板测量；没有加载学生模型权重或启动 GPU 训练。

| 样本 | 反思 tokens | Phase 1 完整序列 | 续推含 boxed tokens | Phase 2 完整序列 |
|---|---:|---:|---:|---:|
| 0.6B k1 | 170 | 722 | 201 | 487 |
| 0.6B k2 | 209 | 1119 | 205 | 544 |
| 4B k2 | 143 | 741 | 191 | 471 |

三条都远低于 4096，也未超过 2048。本次残余问题不是长度限制。

一个 API 对象拆成两种训练目标：Phase 1 使用题目 + 学生原错误回答预测三个反思字段；Phase 2 使用题目 + 三段反思预测续推。最终 boxed 只由 reasoning 与 final_answer 程序拼接；原始 API 回复独立保存。

## 结论的边界

这次 3/3 错误候选的最终数值正确、0/3 反思直接泄漏所求终值；但严格人工可直接使用的示例为 1 条，另外两条需要处理状态来源或修复边界。另有 1 条合理的 incomplete 筛除决定，但审核对象格式未完全合规。

这是同一组四题上的单次抽样，不是总体合格率估计。本轮同时改变了 prompt、输出字段、输入组织和调用次数，不能把差异归因于“单次调用本身更强”。同一次调用也不具备独立诊断与续推上下文隔离；答案正确不能证明学生只凭反思就一定能续推成功。

全部数学复核在本地完成，没有额外 teacher 自评请求；原始响应没有人工修补。summary.json 的 Pending 是运行结束时的机器状态，完成后的人工结论以本报告为准。

完整实际 prompt 保存在 manifest.json 的 assets.annotation.system.txt.text，也对应 `/root/reflection_grpo_clean/configs/sft/teacher_v2_single/annotation.system.txt`。API 凭据经隐藏终端输入，没有写入产物；目录检查未发现凭据模式。
