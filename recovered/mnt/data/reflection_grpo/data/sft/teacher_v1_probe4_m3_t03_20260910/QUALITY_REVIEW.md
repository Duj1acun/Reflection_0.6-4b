# M3 与 M2.7 同题、同 prompt 对照

结论：这 4 条样本中，M3 的数学诊断比 M2.7 更可靠，尤其没有重复错误恒等式，并能识别“等价但未完成化简”的回答。但原样生成的反思仍不适合直接用于本项目的两阶段 SFT：3 条错误诊断都提前给出了最终答案，且存在状态来源与格式问题。不能据 4 条样本推断全量正确率。

## 对照条件与实际执行

- 基线：`/mnt/data/reflection_grpo/data/sft/teacher_v1_probe4_t03_20260910`。
- 本轮：MiniMax-M3；响应中的 model 字段也均为 MiniMax-M3。
- 使用相同的 4 条学生回答；samples.json 与基线逐字节相同，SHA256 为 `3ed242f7340caf082f8139d99275b693434ab81000d3db2648c6768bdabbd805`。
- 四个 prompt/schema 资产与基线完全相同，直接使用基线冻结快照，未修改提示词或评价标准。
- 实际地址仍为 `https://api.minimaxi.com/v1/chat/completions`。
- temperature=0.3，top_p=0.95，max_completion_tokens=16384，timeout=600 秒，小样本并发上限 4，无自动重试。
- 诊断请求的实际差异仅为 model=M3，以及 M3 显式添加 thinking.type=adaptive。两轮都设置 reasoning_split=true；M2.x 的思考默认常开。参数依据 [MiniMax 官方接口文档](https://platform.minimaxi.com/docs/api-reference/text-chat-openai)。这保证输入与采样参数相同，不代表两种模型的内部思考预算完全相同。
- 共 4 次诊断、1 次续推，合计 5 次请求。5/5 HTTP 200，5/5 finish_reason=stop，5/5 返回非空独立 thinking 字段，无截断。
- 两条诊断因最终 content 外包 Markdown 代码围栏而被严格解析器拒收，没有调用续推；一条被正确标为 incomplete，不应进入错误反思续推队列。
- usage 合计：prompt_tokens=13,184，completion_tokens=11,028，total_tokens=24,212。因实际调用次数不同，不能直接把两轮总 token 数当成同任务成本比较。不估算实际账单金额。
- Perfect API 请求 0。未启动全量标注或训练，未修改原始学生回答和判分标签。

## 最重要的进步

分式题中，学生最终表达式为

    ((a²−1)(a+b−1))/((a−b)(a²−a+1)),  a=p/q, b=q/p。

M3 正确利用 b=1/a，得到 a−b=(a²−1)/a、a+b−1=(a²−a+1)/a，确认原定义域内结果等于 1。独立使用 SymPy 对原题表达式和学生表达式化简，两者均为 1。

M2.7 所给错误恒等式在 a=2、b=1/2 时左右分别为 3 与 15/4。M3 没有重复这个错误。这是数学判断的实质进步，不是单纯格式改善。

糖果题中，M3 的平方和方法也正确：每次合并平方和增加 2ab，最终总和仍为 26，所以累计糖果为 (26²−26)/2=325，与顺序无关。最多能执行 25 次合并，剩余一分钟无操作；续推指出了操作次数问题，但“题目本意是 25 分钟”的说法不如直接说明剩余时间无操作准确。

## 仍然不能直接训练的原因

### 1. 反思提前给出答案：3/3 错误诊断均存在

- 糖果题 new_direction 完整算出 `(676−26)/2=325`。
- 固定点题 new_direction 从坐标推到 b，再直接算出最终值 1。
- 系数和题 new_direction 直接代入并算出最终值 -2。

这违反当前反思只保留有效状态、解释错误、给下一步方向的约定。尤其 Phase 2 只看题目与反思，此时正确答案已经通过反思进入输入，无法用这批样本体现真正的纠错续推训练目标。

### 2. 学生已有状态与 teacher 新结论混在一起

糖果题把总和不变、平方和每次增加 2ab 写进 verified_states，但学生错误前没有建立这些结论。系数和题也把修正后才得到的 x=-1 条件放进 verified_states。它们数学上正确，但不符合“学生到目前为止已经得到什么”的来源约束。

### 3. 格式与定位还不稳定

M3 的 4 条诊断只有 2 条 content 可直接作为严格 JSON 解析；另外 2 条是外包 ```json 围栏，而不是 JSON 内部字段结构损坏。人工审核时仅在内存中去掉围栏，5 条响应的对象均通过 schema。此操作没有改写留档，也没有追补续推调用。

3 条 incorrect 诊断中，糖果题和系数和题引用准确，固定点题的引用被改写。固定点题定位 S0017，比 M2.7 的 S0026 更接近最早错误，但 S0015 已经丢失 -8/9。

唯一的续推虽然有正确 boxed 答案，但开头讨论反思质量并大量重述题目与已有分析，仍需按训练目标压缩。仅看答案判分通过，不能替代反思质量验收。

## 统计口径

- 原始格式：3/5 响应严格 JSON 合规，其中诊断 2/4、续推 1/1。
- 人工去围栏后的对象结构：5/5 schema 合规；这是审核信息，不是实际流水线放行数。
- 错误诊断原文引用：2/3 准确（包含人工读取被围栏拒收的对象）。
- 数学审核：这 4 条最终诊断未发现 M2.7 那类错误恒等式或错误合并策略；有 1 条合理的 incomplete 筛除。
- 自动流程形成 1 条诊断—续推配对；续推原文答案提取为 325，本地 compute_math_score=1.0。
- 严格人工验收的可直接训练配对：0 条。3 条错误诊断都因答案泄漏不符合约定，另 1 条应被正确筛除。不能把这写成“M3 数学正确率 0%”。

## 建议

M3 值得作为下一轮候选 teacher，但现在不应直接放大到 7,853 条候选。下一轮优先改进反思字段的职责和示例，严格分离已有状态与新推导，禁止反思完成最终运算；程序可根据选中的来源定位复制原文，并规范化外层代码围栏或使用经验证的结构化输出功能。

这些只是后续建议。本轮没有修改 prompt、放宽实际校验、额外调用 API，或把人工修正冒充模型输出。四条样本每条只测试一次，也未测试“固定同一反思、只更换续推模型”的独立续推对照，不能据此给出总体准确率或单独的续推能力排名。

原始请求、响应、程序结果分别在 calls/、results.json、summary.json。摘要中的 semantic_review 保留程序产生时的 Pending 状态，完成后的人工结论以本报告为准。凭据经隐藏终端输入；产物检查未发现凭据模式。
