# GRPO 速度瓶颈诊断（截至112步）

## 已测得的耗时

第112步总计1699.238秒：采样1546.491秒（91.01%）、奖励判分14.667秒（0.86%）、旧策略概率重算31.031秒（1.83%）、actor更新106.204秒（6.25%），其余少量调度开销。该步不含验证。

前49步平均采样301.26秒、每步生成535,697 tokens；最近12步平均采样1172.98秒、每步生成1,481,971 tokens。输出量增至约2.77倍，单位输出token的采样耗时增加约40.75%，合计采样耗时约3.89倍。
最近12步低截断的4步平均总耗时11.20分钟，高截断的8步平均26.36分钟。

## 已确认的缓存压力

日志中两个vLLM worker累计抢占计数分别至少3201和3001，总计至少6202次事件。计数并非唯一回答数量。警告明确说明KV cache不足，触发RECOMPUTE。
当前参数为gpu_memory_utilization=0.35、每卡max_num_seqs=64、每条最多8192生成tokens。每步64题×8条=512条轨迹，两卡各约256条等待生成。
vLLM预算只占卡显存35%；它不因nvidia-smi显示空闲而自动扩大预分配KV cache。约14 GiB预算也并非全部用于KV，还包含其他推理开销。

从本地Qwen3配置估算：28层×8个KV heads×128维×K/V两份×BF16每元素2字节=每token112KiB。8192-token长序列的KV约896MiB，不含prompt和管理开销。若64条都接近上限，独立生成部分KV就约56GiB，远超当前预算。实际vLLM会动态调度和共享公共prompt，不能把此估算当作实际分配值；它解释了为何长回答密集时需要抢占。

vLLM 0.8.5官方说明：KV不足会抢占请求，并在恢复时重新计算；建议增加gpu_memory_utilization或减少max_num_seqs/max_num_batched_tokens。
https://docs.vllm.ai/en/v0.8.5/performance/optimization.html#preemption

## 验证及其他开销

第100步完整验证耗时4845.78秒（约80.76分钟）；每次540题×4样本=2160条回答，分17批。验证会增加整体墙钟耗时，但不解释第112步的采样变慢。
当前为eager执行，CUDA Graph关闭。其kernel发射和Python调度开销尚未用profiler单独量化，不能承诺切换后的提速倍数。
双卡是TP=1的两个采样副本，collector同步等待各卡整批返回，可能存在长回答尾部等待。尚未逐rank记录每批耗时，不能精确分摊等待比例。

## 采样一致性问题待复现

最近12步，低截断4步的采样/重算概率平均差约0.0045，高截断8步约0.0466；二者相关，但不能仅凭相关性认定权重未同步或缓存已损坏。
检查了本地FSDP-vLLM同步及vLLM 0.8.5源码：每次进入rollout都会load_weights；LLM.sleep会先reset_prefix_cache再丢弃KV。因此不能把“代码未在load_weights后显式reset_prefix_cache”直接认定为跨步旧缓存复用漏洞。
需要在同一checkpoint、同一批题上比较不同缓存压力下的长回答、概率差、抢占计数和耗时。

## 优化顺序建议

1. 优先用相同checkpoint压测KV预算和在途并发数，例如比较max_num_seqs=16/32/64；同时验证采样和FSDP更新阶段的显存峰值。总采样数n=8及训练batch64不必随并发数改变。
2. 查清概率差扩大与重复/异常长回答的关系，不能简单把全部长回答归因为模型能力退化。
3. 在正确性和内存稳定后测试CUDA Graph及验证批调度。
4. 训练数、采样数、学习率、生成token预算和评测口径保持统一；硬件调度优化及测量条件需记录。

本次只检查运行和源码、输出诊断文件，没有修改正在运行的训练配置或重启任务。前期小批次预检未覆盖大量长回答同时生成，这项压力验证不足。
